Okay, so now that we have the single core firmware for the Raspberry Pi Zero 2w working, lets get all four cores running. Why is four cores better than one? We have many tasks that we may want to complete with parallism, rather than just concurrency, in an embedded context. Picture a system where you have flight controls, radar imaging, detonation controls, etc. You may not want all of those in your critical loop. If radar processing takes an unexpected amount of time, we don't want our critical loop to stall. There are multiple ways to handle that, such as watchdogs, but multiple parallel cores opens up a lot of cool things we can do, and imposes little overhead, granted we don't race ourselves into oblivion

First things first, all cores share the same memory addresses, because there is no OS underneath to abstract or restrict the space away from us. Remember, unless we write a filesystem, there isn't one. There is nowhere to put data outside of RAM. We have the RPI-given 512-MB of memory. All four cores can see all 512-MB of memory. We need to give each of them their own stack to start so they don't step on each others toes.

Okay, now we have 16-KB of memory reserved for our four core stack. Stacks grow down, so we grab their lowest address first, increment by 4K, and grab their highest possible address.

Now we can see that they each have their own 4KB to play with, and will not step on each others toes (unless we fuckup. Don't fuck up).

We need to initialize their stacks now, because we currently only handle core 0. Core 0 also has some extra responsibilities that we don't want to race, so we need to jmp the other cores to their own initialization procedure. Here I called it init_stack, and the general flow is:

  1. we need to find the stack top. This is labeled in our linker, and is the highest address of the core 0 stack.
  2. Because we calculate the other stack by just incrementing 4096 bytes each time, we can recalculate here once we know that starting address. For any given core, number N, we can get the top stack address with
N stack top = (core 0 stack top address) + ( N * 4096)

which we place in the x0 register. Remember, each core has its own registers, so each core has its own x0. We are placing the stack location of each core's stack in their own x0, and then moving that into each of their own, unshared stack pointer. Then each core has a stack pointer register that knows where it starts (and from which we can compute an end). 3. Right now we are then hanging the core again

Now, we need core 0 to write the entry addresses into the correct slot, and we need it to send them a wake event.

We can see in their official examples that they use 0xe0, 0xe8, and 0xf0 for the cores. Lets start by just unleashing one extra core

Now, because core 0 is the chosen one and has a super special entry, we can use it to prime the other cores. We branch from bss_done to the kernel_main in our C file, so immediately prior to branching there is a good place to put the multi-core initialization.

So first we need to put the location of the entry function into the x0 register. Then we put the 0xe0 location that we stole from the RPi foundations homework, into x1. Next we store what is in x0, into the address pointed to by x1. dsb is a special ARM instruction that stands for Data Synchronization Barrier, and forces the cpu to wait for all loads, stores, cache ops, and translation lookaside buffer operations to be done. This ensures we don't do anything before the values we expect are actually instantiated. If we don't, a worker could wake up and read its address before it has a value other than 0, and go back to sleep. sev is the Send Event instruction.

flag address = flag base + (core n * 8)

Now, each of these core is currently just writing into their own stack, and that is private. That means our core 0 can't actually access them and tell us any of the values. So instead, I would like to reserve another set of memory address, offset by a size increment times the core number. Once again, this stops the cores from racing, as we can ensure core 1 never writes into core 2's space, core 2 never writes into core 1 or 3's space, and so on. Lets go back into boot.S and add another .bss section. Before we add another toy size section, we should remember this will be a race-free section of essentially "shared" memory, where workers can place and move data around for each other, separate from their private stack. We should also remember that the stack addresses follow the bss section, and will move according to the amount we allocate. I think 64KB per core is a decent place to start, because it gives us a fair amount of memory to use. Now when I say "shared" here, I expect one core to be able to write to one of the four sections, but it is able to read the other 3. We absolutely do not want all 4 cores writing to all four sections of this reserved memory. There is no kernel protection against such writes here (well, we ARE the kernel protection I suppose).
